## How the attacks were made

A saved plan is plain JSON in `<data>/plans/<id>.json`. `cleancraft clean <id> --yes` loads it and runs it with its own digest; MCP `execute_plan` compares the agent's digest with a plain SHA-256 of the file's content, and MCP `get_plan` hands out that digest. So anyone who can write the file (the user, or an agent with file tools) can change items, `locked`, `category` and `group` freely: the only fences left are each feature's allow-list, `policy::check` and `Feature::prepare`. The tests do exactly that (`edit_saved_plan`), and `mcp_execute_plan` / `cli_clean` copy the steps of the MCP tool and the CLI line for line (the mcp crate cannot be a dev-dependency of core).

The fake home is on a case-sensitive Linux disk; macOS volumes are case-insensitive by default, so a folder spelled `documents` in the fake stands for `~/Documents` as macOS resolves it.

## Checked and found right (passing tests, kept unignored)

- `protected_places_are_refused_even_for_home_wide_allow_lists`: with the home folder as allow-list, Documents (itself and inside), Desktop, iCloud Drive, CloudStorage, Photos and iPhoto libraries, keychains, CleanCraft's journal, quarantine and settings, Messages, Notes, the home folder itself, `..` paths, relative paths and `/System` are all refused.
- `symlink_and_hard_link_into_documents_never_reach_documents`: a symlink in Downloads to a Documents folder is not followed by Large & Old Files; an edited plan through the link is refused; the link itself and a hard link to a Documents file may move and the Documents file stays whole; Duplicates ignores the hard-link pair; undo puts the link back as a link.
- `pop_and_on_my_mac_attachments_are_never_proposed_or_moved`: Mail Downloads never lists POP or On My Mac attachments, and an edited plan with them is refused (they are outside the allow-list, which only holds server accounts).
- `privacy_never_preselects_passwords_bookmarks_or_autofill`: Chrome `Login Data`, Firefox `logins.json`, Chromium `Web Data` and Firefox `places.sqlite` (bookmarks) are never preselected; bookmarks and Preferences files are never listed; passwords are listed unselected.
- `ignore_list_is_honoured_by_every_plan_scan`: ignoring every item a scan found removes them all from the next scan, for System Junk, Mail Downloads, Privacy Traces, Startup Items, Threat Check and Duplicates.
- `every_plan_module_puts_back_what_it_moved`: run then undo the whole plan restores every item with its size for System Junk, Mail Downloads, Privacy Traces and Duplicates.
- `trash_bins_and_feature_less_plans_never_move`: a plan for Trash Bins, Tune-up Tasks or Live Monitor holding a Trash item moves nothing; a plan with no feature is refused.
- ui `review_domain_disk_map::documents_and_library_rows_stay_locked`: Select Documents and Select Library tick nothing.

Also read in the code and found matching FEATURES and research (no new test from me; the builders' tests named in FEATURES cover some): Tune-up commands K1-K10 in `tasks::prepare` are the exact FEATURES commands; Startup and Threat Check skip Apple-signed items; Threat Check preselects only high-confidence startup rules and never apps; App Remover marks the maker's shared folder (`Application Support/<vendor>`) as shared and never preselects it; orphan leftovers are checked with Spotlight and never preselected; Mail account types: folder prefix, then Accounts.plist, then Accounts4.sqlite, unknown types locked; Trash Bins has an empty allow-list.

## Observations (not logged as defects)

- K3 "Free up purgeable space" runs `tmutil thinlocalsnapshots / 999999999999 4`, which removes local Time Machine snapshots like K4, but is labelled Low risk with no administrator prompt. FEATURES says so, so it is per contract; worth a second look.
- By the code (an ad hoc or missing signature is a reason by itself), Threat Check will list every Homebrew service (`homebrew.mxcl.*`, ad hoc signed bottles on Apple silicon) and tools under hidden folders (`~/.local/bin`) as findings. Not preselected and per P1, but many developers will see them as false alarms.
- Allow-lists are folder-wide (System Junk: all of `~/Downloads` and `~/Library/Preferences`; Privacy: all of `~/Library/Safari`, every Chromium profile folder, `com.apple.sharedfilelist` incl. Finder favorites). With edited plans that is where DOM-3/DOM-6 style moves land; the root fix is to make the executor re-derive locks (or re-scan and intersect) instead of trusting the saved file, or to sign plans with a key kept out of the plan folder.
- App Remover does not stop (`launchctl bootout`) the launch agents it moves; the helper keeps running until logout.

## Only on a real Mac

1. Case-insensitivity (DOM-1, DOM-11): `ls -d ~/documents` prints `/Users/<you>/documents` and lists Documents on a default APFS volume. Then in CleanCraft Large & Old Files > Another folder type `~/documents`: expected after a fix, "protected"; today it is accepted.
2. lsof names (DOM-8): open `~/Downloads/Invoice (1).pdf` in Preview, run `lsof -F n -w | grep Invoice`: expected `n/Users/<you>/Downloads/Invoice (1).pdf`. Also check how lsof prints non-ASCII names (`Café.pdf`): if it escapes bytes (`\xcc\x81`), the open check misses those files too.
3. Running apps: `ps -axo pid=,comm= | grep Safari` must print the full path `/Applications/Safari.app/Contents/MacOS/Safari`; an app started from a translocated copy (`/private/var/folders/.../AppTranslocation/...`) is not seen as running from `/Applications`, so App Remover could move it while it runs.
4. Root-owned App Store apps (DOM-7): `ls -ld /Applications/Pages.app` shows `root wheel`; try moving it as the user from an edited plan to see whether the rename fails.
5. TCC: without Full Disk Access, `stat` of a program inside `~/Library/Containers/<other app>` fails with "Operation not permitted"; J8 then calls the agent broken. Check with an agent whose program lives in a container (tests run as root here and cannot show it).
